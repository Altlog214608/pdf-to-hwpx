## 2. 발견된 결함 (PDF ↔ HWPX 대조)

| # | 증상 | 예시 | 원인 단계 | 근본 원인 |
|---|---|---|---|---|
| D1 | 시의 **연 구분(빈 줄) 소실** | 1·2·3·4연이 한 덩어리로 붙음 (모든 지문) | parser → IR | `blocks[].start_y` 간격이 19pt(행) / 38pt(연)으로 명확히 다른데 `raw_text` 생성 시 `\n`으로만 이어 붙임 |
| D2 | 줄바꿈 지점의 **띄어쓰기 소실** | `(나)의화자는`, `바람한 자락` | parser | PDF 텍스트 레이어의 줄 끝은 `"(나)의 "`처럼 공백으로 끝나는데 `get_line_records()`가 `.strip()`한 뒤 공백 없이 연결함 |

| D4 | 휴리스틱 때문에 **올바른 띄어쓰기가 망가짐** | `(B) 이 시를` → `(B)이 시를`, `㉠ 와 같다` → `㉠와 같다` | normalizer | `cleanup_punctuation()`의 "괄호/㉠ 뒤 조사 붙이기" 정규식이 `이`/`와`를 조사로 오판함 |

참고 (원본 PDF 자체 문제, parser 버그 아님):
- Q21 ④⑤의 `㉡`가 PDF 텍스트 레이어에서 `㡡`(U+3861)로 잘못 매핑됨. 원본 PDF 화면에도 깨진 글자로 보입니다. 원문자 영역 주변의 CJK 오매핑 보정표로 처리할 수 있습니다.
- `고난도`, `서술형` 섹션 배너(이미지)는 출력되지 않습니다. 의도한 동작인지 확인이 필요합니다.

## 3. 아키텍처 문제

1. **validator가 "구조"만 보고 "텍스트"는 보지 않음.** D1~D6이 모두 있는데도 `status: PASS`. 원본 PDF 텍스트(공백 보정 후)와 HWPX 텍스트를 문자 단위로 비교하는 *텍스트 충실도 지표*가 없습니다.
2. **누적 파이프라인.** `main_v049523()` → `v049518` → `v049519` → `v049523`(→`v049522`→`v049521`→`v049520`) 순으로 각 버전의 finalizer가 같은 HWPX XML을 차례로 다시 패치합니다. `_v049518_build_digit_icon_map = ...`처럼 전역 함수를 재할당하는 monkey patch가 20곳 이상 있습니다.
3. **결과 JSON 10.8MB.** `hwpx_v049517` ~ `hwpx_v049523` 7세대의 검증 결과(각 0.3~1.2MB)와 `render_plan` 7벌이 중복 저장됩니다. 그중 `validation_v049517/19`는 `FAIL`이고 최종은 `PASS`라 사람이 보면 혼란스럽습니다.
4. **Hancom COM 의존.** 기본 HWPX를 만드는 데 Windows + 한글 COM이 필요하고, 실제 서식 대부분은 그 뒤의 XML 후처리가 만듭니다. → 아래 6절 AWS 배포의 최대 걸림돌입니다.
5. **Preview 미갱신.** `Preview/PrvImage.png`가 단일 단, 박스 없음 상태로 남아 있습니다. 탐색기 썸네일이나 웹 미리보기가 실제 문서와 다르게 보입니다.

## 4. 개선 제안 (우선순위순)

### P0 — 텍스트 충실도 (모든 국어 PDF에 공통 적용됨)
1. **줄 연결 시 원본 공백 보존 (D2):** `strip()` 전에 줄 끝 공백 여부를 기록하고, 공백으로 끝난 줄만 공백을 넣어 연결합니다.
2. **글자 간격 기반 공백 복원 (D3):** `rawdict`의 글자 bbox에서 `gap > 0.3 × font_size`이면 공백을 삽입합니다. 이 PDF에서는 8건 모두 이 기준으로 잡힙니다(오탐 0).
3. **조사 붙이기 휴리스틱 제거 또는 축소 (D4):** 텍스트 레이어에 이미 공백 정보가 있으므로, 재띄어쓰기는 "원본에 공백이 없었고 간격도 없던" 경우에만 적용합니다.
4. **연 구분 복원 (D1):** 같은 지문 블록 안에서 `Δy ≥ 1.6 × 중앙값 행간`이면 빈 줄을 넣습니다(IR에 `stanza_break` 표시). 보기 박스(Q14 `글쓰기:` 앞)에도 같은 규칙을 적용합니다.
5. **원문자 아이콘을 문맥과 무관하게 텍스트로 치환 (D5):** 아이콘 → `①~⑤` 치환을 문제/선택지 분할 *이전* 단계에서 페이지 전체에 적용합니다.
6. **지시문 원문 사용 (D6).**

### P1 — 검증 체계
- **텍스트 충실도 validator 추가:** 원본(공백 보정) vs HWPX 텍스트 diff, 문단별 유사도, 공백 차이 수, 빈 줄 수를 측정합니다. 이 지표가 내려가면 FAIL로 판정합니다.
- **골든 IR 회귀 테스트:** 7개(+20문제 기준본) PDF의 IR(JSON)을 사람이 한 번 검수해 `tests/golden/`에 고정하고, 매 버전마다 diff를 냅니다. Hancom 없이 Linux에서 돌릴 수 있습니다.
- 결과 JSON은 **최종 단계만** 저장하고, 디버그용 상세 정보는 `--debug`일 때만 별도 파일로 저장합니다.

### P2 — 구조 정리 (기능 동결 후)
- 단계를 `extract.py`(PDF→글자/선/이미지) → `ir.py`(문제/지문/보기 IR) → `render_hwpx.py`(IR→HWPX) → `validate.py`로 분리합니다.
- 현재 v5.23 경로에서 실제로 쓰이는 함수만 추출하고, monkey patch는 명시적 호출로 바꿉니다. 이전 버전 파일은 git 히스토리에 맡기고 루트에서 정리합니다(`v0_*.py` 70여 개, `requirements_*.txt` 30여 개).

## 5. HWPX 생성 방식 전환 권장 (웹 서비스의 전제 조건)

현재는 `Hancom COM으로 기본 문서 생성 → XML 후처리` 방식입니다. 그런데 최종 서식(2단, 세로선, 보기 박스 borderFill, connect=1, 스페이서, 밑줄, 출전 우측 정렬)은 **이미 전부 XML 후처리가 만들고 있습니다.**
→ COM 단계를 **템플릿 HWPX(header.xml에 스타일 미리 정의) + Python으로 section XML 직접 생성**으로 바꾸면 다음이 가능해집니다.
- Linux에서 완전히 실행 → AWS Lambda/ECS 배포 가능
- 서버용 한글 라이선스 문제 회피
- 결정적 출력, 단위 테스트 가능, 속도 향상
- 최종 시각 확인만 Windows 한글에서 수동으로 진행(현재처럼)

이번 `_run03.hwpx`의 `header.xml`과 `section0.xml`을 템플릿의 출발점으로 쓸 수 있습니다.

## 6. 웹 서비스 / AWS 구성안 (초안)

```
[브라우저] ─ 드래그&드롭 ─▶ CloudFront + S3 (정적 프론트, React/Next 정적 export)
     │  ① POST /jobs  → API Gateway → Lambda: presigned PUT URL 발급, job 생성(DynamoDB)
     │  ② PDF를 S3 uploads/ 에 직접 업로드
     │  ③ S3 이벤트 → SQS → 변환 워커 (ECS Fargate 또는 Lambda 컨테이너, PyMuPDF)
     │        └ 결과 outputs/{job}.hwpx 저장, DynamoDB 상태 = DONE
     └─ ④ GET /jobs/{id} 폴링 → presigned GET URL로 다운로드
```
- 변환 시간: 이미지가 많은 2-5(13MB, 22쪽)는 Lambda 15분 제한에 걸릴 수 있으므로 Fargate를 권장합니다. 가벼운 파일만 Lambda로 처리해도 됩니다.
- S3 lifecycle으로 업로드·결과 파일을 24시간 뒤 자동 삭제합니다(저작권 콘텐츠이므로 중요).
- 업로드 제한: PDF만 허용, 크기 상한(예: 30MB), 페이지 상한.
- 인증과 사용량 제한: Cognito 또는 간단한 API 키, WAF rate limit.
- **전제 조건:** 5절의 COM 제거. Windows EC2 + 한글 설치 방식도 가능은 하지만 비용·라이선스·안정성(COM 잠금, 팝업) 면에서 서비스 운영에 부적합합니다.
- 저작권: 원본 PDF 하단에 「콘텐츠산업 진흥법」 보호 표시가 있습니다. 공개 서비스로 운영하려면 이용약관과 업로드 권리 확인 절차가 필요합니다.
